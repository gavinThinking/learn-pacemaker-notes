第 8 讲的 transition graph 里，每个资源动作最后都落到一个脚本上：资源代理（resource agent）。PostgreSQL、虚拟 IP、文件系统，Pacemaker 本身都不懂，它只会按一套约定调用对应的代理，再读代理的退出码。这套约定叫 OCF（Open Cluster Framework）资源代理协议。本篇看 Pacemaker 怎么调用代理、怎么理解退出码，以及同一个退出码为什么有时算成功、有时算失败。

本篇的版本：Pacemaker 2.1.11。源码结论附链接，只依据文档的会单独说明。

## 一句话

资源代理是一个可执行文件。Pacemaker 用动作名作第一个参数运行它，把资源参数放进环境变量，只看它的退出码，不关心它做了什么。退出码要和**这次动作的期望值**比较才有意义：probe 期望 7，表示「没在跑」，返回 0 不算失败，只说明资源原来就在那里跑着；stop 期望 0，返回 7 就是失败，默认会触发 fencing。写代理时最容易出事的就是这几处：stop 不幂等、monitor 分不清「停着」和「坏了」、动作耗时超过超时值。

## execd 怎么运行一个代理

资源的 class 写成 `ocf:<provider>:<type>`，例如 `ocf:pacemaker:Stateful`。DC 把动作发给资源所在节点的 controld，controld 交给本机的 execd，execd 这样运行代理：

1. **找文件**：在 `OCF_RA_PATH`（默认 `/usr/lib/ocf/resource.d`）下找 `<provider>/<type>`，找不到就报「没装」（[services_ocf.c L123-155](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/services/services_ocf.c#L123-L155)，默认路径见 [configure.ac L481-494](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/configure.ac#L481-L494)）。
2. **传动作**：动作名是唯一的命令行参数，例如 `Stateful promote`（同一段代码 L148-149）。
3. **传参数**：全部走环境变量，见下表（[services_linux.c L419-490](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/services/services_linux.c#L419-L490)）。
4. **排队**：同一个资源同一时刻只跑一个动作，后来的排队等（[execd_commands.c L1413](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/daemons/execd/execd_commands.c#L1413)）。收到 stop 时，先取消这个资源所有的周期 monitor（[L520-526](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/daemons/execd/execd_commands.c#L520-L526)），所以代理不用担心 stop 跑到一半时 monitor 插进来。

<div class="table-scroll">

| 环境变量 | 内容 |
| --- | --- |
| `OCF_RESKEY_<参数名>` | 资源配置里的每个参数，例如 `OCF_RESKEY_pgdata` |
| `OCF_RESKEY_CRM_meta_<名字>` | 这次动作的元信息。最常用的是 `OCF_RESKEY_CRM_meta_interval`：0 表示一次性动作（包括 probe），非 0 是周期 monitor 的间隔毫秒数 |
| `OCF_RESOURCE_INSTANCE` | 资源 ID；clone 的实例会带 `:0`、`:1` 后缀 |
| `OCF_RESOURCE_TYPE` / `OCF_RESOURCE_PROVIDER` | class 里的 type 和 provider |
| `OCF_RA_VERSION_MAJOR` / `_MINOR` | 1 和 1，即 OCF 1.1 |
| `OCF_ROOT` | OCF 根目录，代理用它找公共 shell 函数库 |
| `OCF_EXIT_REASON_PREFIX` | `ocf-exit-reason:`，下文「退出原因」一节用 |

</div>

上游自带的 `Stateful` 代理就用 `OCF_RESKEY_CRM_meta_interval` 区分 probe 和周期 monitor：只在 probe 时重新写一遍 promotion score（[Stateful.in L196-210](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/agents/ocf/Stateful.in#L196-L210)）。

## 退出码

完整列表在 [results.h L165-218](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/include/crm/common/results.h#L165-L218)。右列是这个码**和期望值不一致时**调度器怎么处理，代码在 [unpack.c L3975-4160](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/pengine/unpack.c#L3975-L4160)。

<div class="table-scroll">

| 码 | 源码里的名字 | 意思 | 不符合期望时 |
| --- | --- | --- | --- |
| 0 | `PCMK_OCF_OK` | 成功；monitor 里表示「在跑，非主角色」 | 普通失败 |
| 1 | `PCMK_OCF_UNKNOWN_ERROR` | 说不清的错误 | 普通失败 |
| 2 | `PCMK_OCF_INVALID_PARAM` | 参数在**本节点**上不对 | 硬失败：不再在本节点启动 |
| 3 | `PCMK_OCF_UNIMPLEMENT_FEATURE` | 不支持这个动作 | 一次性动作是硬失败；周期 monitor 记为「不支持」 |
| 4 | `PCMK_OCF_INSUFFICIENT_PRIV` | 权限不够 | 硬失败 |
| 5 | `PCMK_OCF_NOT_INSTALLED` | 本节点缺软件或文件 | 硬失败 |
| 6 | `PCMK_OCF_NOT_CONFIGURED` | 配置本身就错，换哪个节点都一样 | 致命失败：所有节点都不再启动 |
| 7 | `PCMK_OCF_NOT_RUNNING` | 干净地停着 | 普通失败（probe 和非托管资源除外，见下节） |
| 8 | `PCMK_OCF_RUNNING_PROMOTED` | 以主角色运行 | 普通失败；probe 返回它则只说明「原来就是主」 |
| 9 | `PCMK_OCF_FAILED_PROMOTED` | 出错了，而且可能还是主 | 普通失败，并认定它当时仍是主 |
| 190 | `PCMK_OCF_DEGRADED` | 在跑，但状态变差 | 先当成 0 再比较 |
| 191 | `PCMK_OCF_DEGRADED_PROMOTED` | 主角色在跑，但状态变差 | 先当成 8 再比较 |

</div>

几处细节：

- **超出范围的码一律当 1。** 代理返回 0–9、190、191 以外的值，execd 直接改成 1（[services_ocf.c L166-180](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/services/services_ocf.c#L166-L180)）。脚本里 `exit 255` 或者被 `set -e` 带出来的奇怪退出码，集群看到的都是 1。
- **190、191 是「成功但要提醒」。** 调度器先把它们当成 0、8（[agents.c L71-89](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/common/agents.c#L71-L89)），资源照常算在跑；同时把这条记录放进失败动作列表，`crm_mon` 的 Failed Resource Actions 里会看到它（[unpack.c L3984-3991](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/pengine/unpack.c#L3984-L3991)）。
- **硬失败和致命失败的区别是范围。** 硬失败给资源加一条本节点 `-INFINITY` 的 location，ID 是 `hard-error`；致命失败加的是所有节点的 `-INFINITY`，ID 是 `fatal-error`（[unpack.c L5015-5040](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/pengine/unpack.c#L5015-L5040)）。这两条约束不写进配置段，是调度器每次计算时从那条失败记录推出来的：用 `crm_resource --cleanup` 清掉记录，或者一次性动作的失败记录按 failure-timeout 过期（[unpack.c L4643-4672](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/pengine/unpack.c#L4643-L4672)，第 11 讲），约束才消失。所以 2 和 6 不能乱用：源码注释里 2 是「在本节点的环境下不成立」，6 是「本身就不成立」——参数漏填或写错用 6，参数指向的东西只在这台机器上不存在用 2。
- **9 和 1 的区别在角色。** 返回 9 时调度器认定这个实例当时仍是主（[unpack.c L4108-4113](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/pengine/unpack.c#L4108-L4113)），恢复时按主角色的实例处理。

## 期望值：同一个码，可能成功也可能失败

调度器排每个动作时就定好了期望的退出码，写进 transition key 随图下发（第 8 讲）。结果回来后，退出码等于期望值就记为成功，不等就记为失败，再按上一节的表分档（[unpack.c L4040-4058](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/pengine/unpack.c#L4040-L4058)）。

<div class="table-scroll">

| 动作 | 期望值 | 出处 |
| --- | --- | --- |
| probe，调度器认为资源没在这个节点上 | 7 | [pcmk_sched_probes.c L28-41](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/pacemaker/pcmk_sched_probes.c#L28-L41) |
| probe，认为它在这里且是主 | 8 | 同上 |
| probe，认为它在这里，不是主 | 0 | 同上（不设就是 0） |
| start、stop、promote、demote、notify | 0 | — |
| 非主角色的周期 monitor | 0 | — |
| 主角色的周期 monitor | 8 | [pcmk_sched_recurring.c L343-346](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/pacemaker/pcmk_sched_recurring.c#L343-L346) |
| Stopped 角色的周期 monitor（在不该运行的节点上定期确认它没跑） | 7 | [pcmk_sched_recurring.c L545](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/pacemaker/pcmk_sched_recurring.c#L545) |

</div>

probe 是例外：它的任务是发现现状，所以返回 0 或 8 而期望是 7 时，调度器不算失败，只记一条 `Probe found ... active on ...`，此后把资源当成在这个节点上跑着（[unpack.c L4061-4105](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/pengine/unpack.c#L4061-L4105)）。如果资源只该跑一份，调度器下一张图就会安排把多出来的那份停掉。

7 只在三种情况下不算失败：probe、期望值本来就是 7、资源处于非托管状态（[unpack.c L4074-4089](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/pengine/unpack.c#L4074-L4089)）。其余时候返回 7 都是失败，包括 stop。

execd 一侧对 OCF 代理的退出码不做改写；controld 收到 7、8、190、191 时也不下结论，注释原文是「Leave it to the TE/scheduler to decide」（[controld_execd.c L2297-2310](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/daemons/controld/controld_execd.c#L2297-L2310)）。成败只在调度器里判定一次。

## 代理最容易写错的三处

**stop 必须幂等。** 资源已经停了，再调 stop 也要返回 0，不能返回 7。stop 的期望值是 0，返回 7 就是失败；stop 失败时 on-fail 的默认值是 fencing（集群启用了 fencing 时），没启用 fencing 就是 block，资源停在原地不再管理（[pe_actions.c L999-1006](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/pengine/pe_actions.c#L999-L1006)）。如果 stop 返回 2、3、4、5 而这个节点又不能被 fencing，调度器记 `No further recovery can be attempted`，把资源设成非托管并阻塞，只能人工处理（[unpack.c L3905-3931](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/pengine/unpack.c#L3905-L3931)）。start 也一样：已经在跑就返回 0。

**monitor 要分清「停着」和「坏了」。** 资源干净地停着返回 7，出了问题才返回 1。集群启动或节点加入时，调度器会在每个节点上 probe 每个资源，期望 7。一台从没装过这个服务的节点如果返回 1，调度器就认为资源在这里处于失败状态（[unpack.c L3868-3875](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/pengine/unpack.c#L3868-L3875)），要去这里执行 stop——一个本来就不存在的资源，被安排了一次恢复。

**动作要在超时内结束。** 每个动作的超时默认 20 秒（[actions.h L37-38](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/include/crm/common/actions.h#L37-L38)），在资源的 op 定义里用 `timeout` 改。代理进程启动时自成一个进程组（[services_linux.c L1000](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/services/services_linux.c#L1000)），超时后 execd 对**整个进程组**发 SIGKILL，不先发 SIGTERM（[mainloop.c L1064-1080](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/common/mainloop.c#L1064-L1080)）。脚本里的清理代码、trap 都来不及跑，它启动的子进程也一起被杀。这次动作记为超时，日志写 `timed out after`（[services_linux.c L727-735](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/services/services_linux.c#L727-L735)），调度器按失败处理。stop 超时同样默认 fencing。所以代理内部的等待要比 `timeout` 短，PostgreSQL 这种停库可能要几十秒的服务，stop 的 `timeout` 要按最坏情况配。

## 退出原因

退出码只有一个数字。代理想说清楚为什么失败，就往 stderr 打一行 `ocf-exit-reason:<原因>`，公共函数库里的 `ocf_exit_reason` 做的就是这件事。execd 取 stderr 里**最后一次**出现的这个前缀，读到行尾，最多 128 个字符（[services_linux.c L646-690](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/lib/services/services_linux.c#L646-L690)）。这段文字存进 lrm_rsc_op 的 `exit-reason`，出现在 `crm_mon` 的失败动作和调度器日志里。`Stateful` 的 monitor 里有个测试用的写法（[Stateful.in L190-194](https://github.com/ClusterLabs/pacemaker/blob/Pacemaker-2.1.11/agents/ocf/Stateful.in#L190-L194)）：状态目录下有 `.rc` 文件时，直接用文件里的数字作退出码，并附一条退出原因。

## 回到主线

两节点集群，node1 断电，node2 已经当选 DC，fencing 了 node1，调度器算出的图里要在 node2 上 promote PostgreSQL（第 8、9、12 讲）：

1. node2 的 controld 把 promote 交给本机 execd。execd 设好 `OCF_RESKEY_*`，运行 `<代理> promote`，开始计时；
2. 代理在超时内把备库提升为主库，返回 0。期望值是 0，成功；图里排在它后面的动作，比如 VIP 启动，才被放行；
3. 调度器给新主库排一个主角色的周期 monitor，期望 8。代理此后每次 monitor 都要返回 8；返回 0 说明它其实没当上主，返回 7 说明进程没了，两者都是失败，交给第 11 讲的 on-fail；
4. promote 如果超过超时值，进程组被 SIGKILL，这次 promote 记为失败，同样进入第 11 讲的处理。
